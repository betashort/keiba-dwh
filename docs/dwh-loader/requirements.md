## 1. このアプリですること

収集アプリとは別のプロセスとして、書き込みが完了した生データだけを読み、更新があるたびに解釈した行を PostgreSQL に書く。利用者はそのたび起動しない。

1. `complete = 1` の raw と、それを指す索引だけを読む。
2. 推奨キーとデータ作成年月日で、どの行を最新とするか決める。
3. 2023-08-08 前後のフィールド長の違いを吸収する。
4. `RACE` の確定成績と、`0B12` / `0B15` の速報の優先を決める。
5. `0B14` は、台帳が持つ最新世代だけを有効にする。
6. 解釈済みの行を PostgreSQL に書く。
7. 完了した生データに更新があったとき、1 から 6 を人手なしで行う。

馬券予想モデルの起動は、ローダの仕事に含めない。開始の契機と、フルのデータを入力にすることは [../requirements.md](../requirements.md) が定める。ローダは、その実行が読む行を、速報を含めて倉庫へ載せ終える。

やらないこと:

- JV-Link の呼び出し
- 収集アプリのプロセスへの組み込み
- 完了済み raw の書き換え
- 利用キーの保持と、収集アプリの水位を進めること
- 予想の計算、モデルの起動、投票、収支の計算

未知のレコード種別は収集側が残している。採否はローダが決める。

## 2. 入力と設定

読む場所は `DataRoot\raw` と `DataRoot\state\ledger.sqlite` だけである。フレームの並びと台帳の中身は、収集アプリの設計のランディングを正とする。

接続のホスト、ポート、データベース名、認証はローダの設定に置く。収集アプリの `config.json` には置かない。PostgreSQL は収集アプリと同じ PC で動かす。採用の理由は [warehouse.md](warehouse.md)。

## 3. 守ること

- 完了していないファイルを読まない。
- 収集アプリが完了済みファイルを書き換えないことに依存してよい。
- 生バイトの正本は raw に残し、PostgreSQL には解釈後の行を置く。
- 収集アプリの画面とログに、ローダの接続情報を出させない。
- 完了した生データの更新に追随する。ファイルごと、速報ごとに利用者へ起動を求めない。

## 4. できていると言える条件

1. `complete = 1` でない raw からは行を作らない。
2. 接続情報はローダの設定にあり、収集アプリの `config.json` には無い。
3. 同じ推奨キーに複数の版があるとき、データ作成年月日に基づいてローダが最新行を決める。
4. `0B14` は、台帳の最新世代に属さないレコードを有効な行にしない。
5. 収集アプリを停止しなくても、完了済みファイルだけを読んで PostgreSQL に書ける。
6. 収集アプリが raw を完了にしたあと、利用者がローダを起動しなくても、そのファイルから作る行が PostgreSQL に入る。
7. 馬券予想モデルの起動は行わず、速報の行を書き終えた PostgreSQL を、全体の要求が定める予想の実行が読めるようにする。

テーブル、主キー、区分の残し方は [schema.md](schema.md)。定義書が確定するまで、テーブル単位の受入条件は置かない。
